# 性能测试报告

## 一、测试环境

| 项目 | 信息 |
|------|------|
| **服务器** | 云主机 (VM-0-13-ubuntu) |
| **操作系统** | Ubuntu |
| **压测工具** | wrk |
| **网络库** | 基于 Reactor 的 C++ TCP 网络库（默认配置） |
| **测试接口** | `http://127.0.0.1:1315/1`（简单 HTTP 响应） |
| **测试方式** | 回环地址（127.0.0.1），排除网络延迟 |

## 二、测试场景与结果

### 2.1 短连接压测

每个请求完成后立即关闭 TCP 连接。

**压测命令：**
```bash
./wrk -c500 -t60 -d60s http://127.0.0.1:1315/1
```
- 并发连接数：500
- 线程数：60
- 持续时间：60 秒

**结果（多次平均）：**

| 指标 | 值 |
|------|-----|
| 总请求数 | ~71,600 |
| **QPS** | **~1,180** |
| 平均延迟 | 430 ms |
| 最大延迟 | 1.76 s |
| 延迟标准差 | 420 ms |
| 超时错误 | 57~380 次 |
| 读/写错误 | 0 |

**典型输出：**
```
Requests/sec: 1193.69
Transfer/sec: 68.78KB
Latency: avg 434.55ms, max 1.80s
Socket errors: timeout 100
```

### 2.2 长连接压测

复用 TCP 连接发送多个请求（HTTP Keep-Alive 行为）。

**压测命令：**
```bash
./wrk -t8 -c500 -d60s http://127.0.0.1:1315/
```
- 并发连接数：500（长连接）
- 线程数：8
- 持续时间：60 秒

**结果：**

| 指标 | 值 |
|------|-----|
| 总请求数 | 5,212,424 |
| **QPS** | **86,734** |
| 平均延迟 | 6.36 ms |
| 最大延迟 | 58.86 ms |
| 延迟标准差 | 5.13 ms |
| 超时错误 | 0 |
| 读/写错误 | 0 |

**典型输出：**
```
Requests/sec: 86734.32
Transfer/sec: 5.29MB
Latency: avg 6.36ms, max 58.86ms
```

## 三、对比分析

| 场景 | QPS | 平均延迟 | 最大延迟 | 超时 | 适用场景 |
|------|-----|---------|---------|------|----------|
| 短连接 | ~1,200 | 430 ms | 1.8 s | 有 | 低频临时请求 |
| 长连接 | **86,734** | **6.4 ms** | 59 ms | 无 | 高频持续交互 |

**性能差异原因：**
- 短连接每次请求包含 TCP 三次握手 + 四次挥手，增加 2~3 个 RTT。
- 长连接复用 fd，减少系统调用和内存分配。
- 本库的 epoll + 非阻塞 IO 在长连接场景下优势显著。

## 四、对本网络库的评价

- **短连接场景**：表现一般，主要是协议自身开销大。可通过启用 `SO_REUSEADDR`、`TCP_FASTOPEN` 或增加工作线程改善。
- **长连接场景**：**性能优秀**（8.6 万 QPS），证明：
  - 事件驱动模型高效
  - Buffer 管理合理
  - 时间轮对性能影响极小

## 五、优化建议（针对短连接）

如果业务以短连接为主，建议：
1. 在应用层启用 Keep-Alive 复用连接。
2. 增加工作线程数（`Set_Slave_Thread_Cnt` 设为 CPU 核心数）。
3. 调整内核参数：
   ```bash
   sysctl -w net.ipv4.tcp_tw_reuse=1
   sysctl -w net.core.somaxconn=8192
   ```
4. 考虑连接池或升级到 HTTP/2。
